# Workers 充值接口接入

本文适用于 `worker/` 的平台代收与自动直充适配器。Go 后端是另一套实现，配置和验证应分别进行。

## 接入与开关

在被 Git 忽略的 `.dev.vars` 中配置独立的 API 地址、代理身份和签名密钥。以供应商当前协议和本账号已授权目录为准；示例配置不包含真实服务凭据。

- `RECHARGE_API_BASE`：HTTPS 地址，路径以 `/v1` 结尾。
- `RECHARGE_PARTNER_ID`、`RECHARGE_KEY_ID`、`RECHARGE_CLIENT_SECRET`：服务端认证。
- `RECHARGE_PRODUCT_MAP`：本站套餐到供应商商品代码的映射。
- `RECHARGE_WEBHOOK_SECRET`：独立回调验签密钥。
- `RECHARGE_NOTIFY_URL`：在供应商处预登记的 HTTPS 地址，路径为 `/api/recharge/webhook`。
- `RECHARGE_PAYMENT_CODE_ENABLED=true`：通过签名的 `POST /v1/orders/{id}/payment-code` 获取支付宝付款码。默认关闭，保留旧收银页桥接方式。

真实购买还需 `ORDER_TESTING_ENABLED=false`、`RECHARGE_CHECKOUT_ENABLED=true` 以及完整有效的回调配置。开发期间保持真实购买关闭。平台代收使用供应商的支付通道，无需配置本站支付宝私钥。

先通过只读接口核对代理状态、自建充值权限、商品授权和支付方式。固定价通道拒绝 `quote_required=true` 的商品，不能用占位供货价创建订单；这类商品需要另行实现付款前预检与报价绑定流程。历史字段 `max_sale_price` 不再作为零售价格上限，供货成本与代理成本校验仍然生效。

## 2026-11-13 接入包兼容

依据用户提供的 `quefa-partner-integration-kit (1).zip`、完整接入文档及 OpenAPI 实现。签名示例与旧包一致，不更换既有代理身份、密钥、回调、支付渠道或商品映射。

- 原菲律宾 SKU 的新订单可由上游切换实际渠道。本站继续发送 `delivery_mode=auto_recharge` 和 `/redemptions` 顶层 `mode=auto_recharge`，由上游按原订单冻结渠道分派，不从 SKU 后缀猜测 direct/cdk，不在失败时另建订单或换渠道。
- 新提交原样转发完整 Session JSON，保留 `accessToken`、`account_id/accountId/account.id`、`user.email` 等身份信息。已有未知结果的 access_token 提交仍恢复原 token 字节和原幂等键，不能在同一键下擅自改成完整 JSON。若上游明确以 HTTP 422、不可重试的 `full_session_required` 拒绝，标记本次未受理并保留安全提示，客户可在同一已付款订单用新尝试补充完整 JSON，不需再次付款。
- 明确终态的原单重提以 `retry_allowed=true`、`next_action=resubmit` 为准，退款处理仍关闭入口；不再把 CDK 专属 `fallback_recharge_available=true` 当成 direct 的重提条件。运行中、结果未知或查询失败不会因此获得新尝试权限。
- 固定价通道只接受实时授权目录中可售、CNY、正供货价并支持自动直充的商品。未定价零金额草稿、动态报价商品保持不可售；独立渠道二 SKU 只有在真实授权目录返回且由商家配置映射后才可使用，不因文档列出 SKU 而自动上架。
- 通用签名客户端识别商品/CDK 预检的 HTTP 202 `preflight_pending` 错误信封，明确尚未通过，给出至少 5 秒等待信息，绝不把它当成 `check_id`，不自动重试金融写入。**本站当前仍是付款后提交 Session 的流程，没有启用付款前异步预检、报价绑定或 CDK 兑换界面。** 若将来启用该流程，仍需独立实现有限串行查询、每次新签名、取消、有效期和报价绑定，不能直接开启动态报价商品。
- 本次适配运行在 Cloudflare Workers；Go 服务的预检/履约实现没有随此变更更新。Session 留存与原资料复用保持关闭。

## 付款与凭据

签名付款码使用原平台订单生成稳定幂等键，请求正文固定为 `{}`。响应必须与原订单号、商户订单号、人民币金额及有效期一致。只接受官方支付宝二维码地址，不把平台收银链接或供应商图片原样交给浏览器；前端沿用本地绘码。付款码生成成功不代表付款成功，付款状态仍须核对签名查单结果。

充值提交请求体最多 256 KiB，提取后的令牌最多 128 KiB 字符。接受原始令牌或受支持的 JSON 包装，已有完整 Session JSON 继续兼容。前端允许至少 256 KiB 原始输入，不使用 textarea maxlength 静默截断；对完整序列化请求的 UTF-8 大小另行校验，超限明确提示。前端仍要求核对账号邮箱；提交前的过期检查只作拒绝提示，不能证明账号有效。重传保留原凭据字节及原幂等键；新的合法尝试使用新键。原始凭据不写入日志或普通订单元数据。启用下文的原资料重试时，仅将原始请求加密存入专用表，不回显给前端。

## 查单与迁移

迁移 `0044_recharge_api_read_backoff.sql` 仅保存账号、资源路径及下次允许查询时间，不缓存供应商响应或凭据。`0045_recharge_remote_attempt.sql` 分别保存本地提交序号与平台任务序号；平台未受理的提交仍保留本地历史，不会消耗平台任务序号。订单与充值任务的通知核对水位也分别持久化，避免两个资源的退避时间错开后一直无法完成同步。升级时先备份数据库并应用迁移，再重启服务：

```sh
npx wrangler d1 migrations apply gptibo-local --local
```

生产数据库需使用自己的资源配置和部署流程。适配器按资源保存 `X-Poll-After` 与 429 的 `Retry-After`/`error.retry_after`；只有停止提示而无时间时使用 300 秒间隔。服务请求在等待期内返回安全重试提示，不向上游重复发送读取。成功的业务写入清除对应资源的本地等待时间，允许重新核对。终态订单仍保留财务核对能力，以发现迟到退款。

前端 `poll` 和 `query` 均查询原订单。并行读取订单与充值任务时，成功返回的状态会单独保存；任何付款、退款和收益冻结条件继续约束本地交付。付款码与有效期未改变时保留已有二维码，刷新暂时失败不会清空仍有效的付款码。

迁移 `0056_recharge_subscription_hint.sql` 为失败任务增加订阅到期提示。只有 `account_has_subscription` 的已失败任务，且原始说明含已识别的 `GPT_PLAN_ALREADY_ACTIVE` 标记及合法日期时，才提取日期数字。原始错误报文不存储、不返回。上游未提供时区的时间仅作提示，不能转换为北京时间、触发自动重试或解除付款及履约限制；是否允许重新提交仍以原任务的重试授权为准。旧失败订单在下一次正常查询原任务后补齐提示。

后台“审批并提交平台退款”使用原退款单和幂等键，平台受理后保持待确认，直到原单查账确认已退。若平台已退款但本地没有售后单，定时任务会重新读取原单，再原子写入售后记录、累计退款和代理收益扣回；也可通过管理员鉴权的同源 `POST /api/admin/refunds/reconcile-external`（JSON 正文 `{}`）触发。这一步只核销已发生的退款，不发起退款。存在未结束售后或待处理提现时保留冻结，需先处理相应记录。

`scheduled()` 必须另行配置定时触发器；服务进程运行本身不代表已启用定时任务。

## 验证边界

相关离线回归测试：

```sh
node --test tests/recharge.test.ts tests/recharge-credential.test.ts tests/checkout-session.test.ts tests/credential-expiry.test.ts
npm test
npm run build
npm run lint

```

模拟接口测试不能证明真实支付、充值或退款已通过。开启真实交易前，在隔离环境验证订单、付款码、到账、充值结果、回调重放与乱序、退款、结算及故障恢复。真实付款测试应单独确定账号、金额和范围。

## 原资料重试与重新提交 Session

迁移 `0058_recharge_saved_credentials.sql` 新增专用加密表和删除触发器。使用既有 `CDK_ENCRYPTION_KEY` 的 AES-GCM 资料库，加密上下文同时绑定本站订单号和本地尝试编号；加密密钥缺失或与原库不匹配时，界面不提供保存能力，服务端拒绝要求保存的提交，不降级成明文。

`RECHARGE_SAVED_CREDENTIALS_ENABLED` 在未配置时默认关闭。主站本次已显式开启，兼容回退版设为 `false`。部署及回退记录见 [原订单重试上线记录](recharge-retry-production-release.md)。关闭时前台只提供重新提交 Session；即使旧页面提交 `retainCredential:true`，也只执行普通充值而不保存资料。`retry-saved` 请求被拒绝，不联系上游；每分钟任务在活跃提交结束后清除旧快照，不修改支付、尝试记录或订单状态。

开启开关且加密库可用时，已付款订单的 Session 表单默认勾选加密保存，客户可以取消。同一个订单表单打开期间保留客户的选择。`submit` 在 `retainCredential:true` 且账号已确认时，事务内保存尝试、审计与密文，再转发上游。保存的新资料覆盖旧资料；不保存的新提交清除旧快照。接口只返回元数据。若加密阶段失败，接口返回 `recharge_retention_unavailable`，此时尚未转发充值。订单弹窗保留本次输入，客户可以取消保存后继续。

原尝试允许重试且原资料可用时，订单提供「使用原资料重试」和「更换 Session 后重试」。复用请求为 `action:retry-saved`，携带稳定请求 key、页面显示的 sourceAttemptId 及账号确认。权限由原订单的买家 Cookie 或已验证邮箱会话校验。服务端在原充值锁内重新查询付款和原任务；查询失败或被上游要求退避时停止。仅明确允许补发的终态可创建新的充值尝试，沿用同一笔已付款订单。上游明确拒收时，同一事务内清除该次尝试的密文，客户可换新资料提交。旧的拒收快照由定时清理移除。

结果未知时只能恢复原请求、原幂等键；即使本地令牌到期提示已经触发，也只能核对这一笔原提交，不能凭此创建新尝试。新尝试仍检查凭据有效期，上游明确报告 Session 无效或本地到期提示成立时要求重新提交。旧页面的原资料按钮不能复用后来替换的快照。所有重试仍尊重退款、资金核对、停止兑换、终态和并发保护。

保存期限最多为首次保存该份资料起 30 天，点击复用不会延期。Session 可能提前失效，期限不代表有效性保证。充值完成、本站或上游出现退款、停止兑换时由数据库触发器清除；每分钟清理到期快照，活跃操作完成后再清理。这里的删除指运行数据库，历史备份依照备份保留策略自然到期。恢复备份后应先运行到期清理与上游状态核对，再允许提交。之前未保存的历史资料无法补回，需用户重新提交一次。

本功能仅适配 Workers 的平台代收充值；Go 后端需要独立实现。`tests/recharge.test.ts` 覆盖密文与接口隔离、同单复用、原请求恢复、替换/取消保存、失效、退款与删除、查询退避、并发和事务回滚；本机 `/__preview/session-precheck` 的原资料重试、资料失效、核对原提交和保存授权场景仅使用合成数据和模拟传输，不发起真实充值。

## Codex 点数包

`0059_codex_credits.sql` 新增 `codex-credits-250`（250 点，¥99）和 `codex-credits-500`（500 点，¥199），商品路由 `/product/codex-credits`。两者是一次性点数包，不属于月度订阅或 Codex 接码。既有订单、订阅映射和自营收款渠道不变。新规格暂不开放代理转售，需另行核定代理成本后启用。

用独立配置 `RECHARGE_CODEX_PRODUCT_MAP` 增加点数映射，避免覆盖已有 `RECHARGE_PRODUCT_MAP` 密钥绑定：

```json
{"codex-credits-250":"chatgpt_codex_250_cdk","codex-credits-500":"chatgpt_codex_500_cdk"}
```

接入包版本 2026-11-13 说明两种交付：`cdk` 模式交付平台品牌的公开 `voucher_code`，用户仍需兑换，发码不等于点数到账；`auto_recharge` 模式付款后提交完整 Session JSON，由平台完成账号充值，前台不交付兑换码。2026-11-14 只读核验两款上游商品的 `delivery_modes` 均含两种模式。本站沿用后者与平台代收支付宝流程，供应目录虽然标记 `fulfillment_mode: cdk`，不据此猜测前台交付方式。

下单时重新读取商品可售状态、固定供货价与实际支持的交付模式，冻结规格、数量 1、零售价与账号；未知提交只核对原幂等请求，只有上游 `succeeded` 才完成交付。Session 留存与同单复用遵循上述可选开关。模拟测试验证支付与履约状态、重复提交、权限隔离和报价变动拦截；未进行真实点数充值，不把模拟结果当成真实到账证明。

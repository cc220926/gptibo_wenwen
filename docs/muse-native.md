# Muse 原生供货 API

适用于当前 Cloudflare Workers + D1 部署，不是 Go 后端适配器。协议来源为 [GPTibo 渠道工作台原生 /v1 文档](https://api.gptibo.com/#native-api-guide)，2026-11-08 读取。不要混用 Dujiao / 异次元兼容协议。

## 供货与价格

服务端固定访问 `https://api.gptibo.com/v1`，人民币分整数。每单采购一份成品号，不传 quantity、客户邮箱、Session 或密码。商品代码、价格、enabled、available 和 account_delivery 类型以当前渠道 GET /products 为准，不使用文档示例的默认价。

本次只读联调发现精品手搓代码为 `muse_1b_pro`，渠道价 800 分；`muse-account-31b` 为 4900 分；示例 `muse-account` 已停用。这是当时的渠道快照，不是固定价格保证。用户选择精品手搓零售价 3500 分、采购上限 800 分，暂不实际采购。新规格暂停销售；旧本地库存不切换货源。

## 配置

应用 `0057_muse_native.sql`。通过 Wrangler Secret 配置 `MUSE_KEY_ID`、`MUSE_API_SECRET`，保留现有 `CDK_ENCRYPTION_KEY`、邮件和自营收款配置。密钥只从忽略的本机安全文件写入，不在源码、前端、数据库采购正文或日志保存 Secret。

首次正式销售须同时满足 `SERVICE_CHECKOUT_ENABLED=true`、`MUSE_CHECKOUT_ENABLED=true`、`MUSE_ACCOUNT_PAYMENT_APPROVED=true`，并配置可用的自营收款、邮件和加密密钥。收款渠道必须明确允许销售 Muse 成品账号；此前兑换码的许可不能自动沿用。

本次用户已确认账号类商品收款许可，但要求不发起采购，因此 `MUSE_CHECKOUT_ENABLED=false`，新规格 enabled=0，商品隐藏状态保留。渠道余额查询成功不等于已完成真实交付验收。

后台「自有商品与库存」显示供货价、可购状态与渠道余额。新建规格选择「Muse 原生 API 自动采购」，填写官方商品代码和采购上限。货源与上限保存后不允许改变，需要时新建规格；可编辑售价、说明及销售状态。采购成本不下发到公开目录。

## 支付到交付

1. 创建订单时查询商品、余额与预检，不扣款、不预留上游库存。事务保存商品说明、原始采购 JSON、Key ID、本站订单号、固定幂等键和预期采购价。采购价须不高于上限且低于零售价。
2. 生成付款码前重新检查供货价格、可购状态与余额。此后供货仍可能变化；上游拒绝原采购时转原订单售后，不能承诺库存已被上游锁定。
3. 支付渠道核验原订单号、金额和收款结果后，原订单进入自动采购。网络调用前持久化 attempted，使用同一 Key、订单号、幂等键及原始 JSON；只更新签名时间和 Nonce。
4. 响应丢失先精确查询 `/orders/by-merchant/:number`。原单不可见时只恢复已保存的同一请求，不能换 Key / 商户单号 / 正文重买。已保存 remote_id 后只查原单；Key 变化时停止自动处理，联系供货方核对并恢复原 Key，不能盲目重提。
5. 原单 succeeded 后核对商户订单号、商品、预期金额、供应商单号，再从原单 delivery 读取一份内容；核对关联与 quantity=1 后 AES-GCM 加密保存。订单、交付内容和事件事务提交，邮件独立重试。成功交付账号资料不等于客户已登录或账号已订阅成功。

不确定采购或取货失败继续查原单，不自动退款或再买。明确失败允许原订单售后；ZPAY 仍须按已实现的人工退款流水核验流程处理。邮件已受理不代表已进入收件箱。

采购锁和持久化不确定状态同时阻止售后与禁用兑换操作，避免已扣采购款后退款仍在发货。已付款但本地预留已到期的订单进入人工核对，不自动采购。旧本地库存和人工服务保留原交付路径。

## 查询、回调和故障恢复

定时队列每分钟补查，订单页刷新按至少 20 秒节流；每轮最多 10 笔待采购，排除未付款订单。按渠道共享每分钟 240 次总请求、10 次预检、50 次取货，给官方限额留余量。异常逐步退避至 5 分钟；限流至少等待 1 分钟。

可选在供货平台「订单回调」配置 `https://你的商城域名/api/muse/webhook` 及至少 32 字符的独立 Secret，并写入 Worker Secret `MUSE_WEBHOOK_SECRET`。本次未替用户配置供货平台回调，轮询可独立完成恢复。入口对原文、时间和事件 ID 验签，事务去重后唤醒队列，再用签名 GET 确认原单。通知内容不直接触发成功或交付，不保存账号原文。重复或乱序通知不会把终态退回执行中。

后台原订单可「核对原采购单」，不提供更换采购编号或手工替换供应商交付内容的入口。API 认证或商品绑定错误时，应恢复原配置；不要删除采购记录、换 Key 或重新创建业务订单。

## 验收

`tests/muse-native.test.ts` 使用模拟供货、支付结果与邮件，验证官方八行签名、真实格式商品代码、原单恢复、金额与交付归属、并发幂等、事务回滚、加密和客户隔离、退款互斥、价格检查、共享限流与回调验签去重。既有支付和本地库存另跑回归。

正式开放前需要足额渠道余额、一笔实际收款与采购交付验收，并确认该 SKU 实际交付字段、账号额度、登录要求和售后范围。不能把已有本地库存规格的「接码链接 / 10 亿 Token」承诺直接当作新供货 SKU 的已验证能力。
